# Файловый ассистент — Day 34

`/day-34` открывает Flash Files. Ассистент читает текущие файлы проекта,
ищет по нескольким файлам и подготавливает документацию. Модель сама выбирает
инструменты локального stdio MCP; shell и публикация в GitHub недоступны.

## Сценарии

1. **Поиск использований.** «Найди использования ConversationSidebar в
   исходниках. Покажи пути и строки». `search_files` выполняет буквальный
   поиск, затем `read_file` даёт контекст. Это поиск подстроки, не AST-анализ:
   алиасы и динамические обращения могут потребовать дополнительных запросов.
2. **Обновление документации.** «Прочитай src/lib/project-mcp-server.ts и
   docs/mcp.md, подготовь обновление раздела о сервере». Ассистент читает
   текущий код и документ, затем предлагает точечные замены с diff.
3. **Создание файла.** «Изучи src/lib/file-assistant-files.ts и подготовь
   docs/adr/file-access.md». Новый Markdown появляется на диске после
   применения предложения пользователем.

Каждый запрос независим; история и трассы видны до обновления страницы.
Отмена останавливает модель, но уже подготовленное предложение может остаться
на странице. Подготовка сама по себе не меняет целевой файл.

## Работа с diff

Проверьте путь и diff в карточке под ответом, затем нажмите «Применить».
Сервер загружает сохранённое предложение по ID: браузер не передаёт новое
содержимое, путь или хеш. Перед записью проверяются корень проекта, ветка,
HEAD, срок предложения и SHA-256 текущего целевого файла. Срок — один час.

При конфликте запись отклоняется с HTTP 409. Задайте новый запрос, чтобы
ассистент перечитал актуальные данные и подготовил новый diff. Проверка
целевого файла не подтверждает, что исходники, использованные для документа,
остались прежними: если код менялся, обновите предложение.

Новый файл публикуется через эксклюзивное создание ссылки на полностью
записанный временный файл; существующий заменяется атомарным `rename`.
Повторное применение того же ID подтверждает прежнюю запись, если содержимое
не менялось. Несколько предложений применяются отдельно, общей транзакции
на несколько файлов нет.

## Инструменты и границы доступа

Режим `files` запускает `scripts/project-mcp-server.ts <root> --files`.
Режим Day 31 без этого флага сохраняет прежние пять инструментов только
для чтения. Файловый режим объявляет:

- `git_branch`, `git_status`, `list_files` — ветка и структура tracked-файлов;
- `read_file(path, startLine?, endLine?)` — UTF-8, диапазон строк, хеш всего
  файла, `totalLines` и `truncated`;
- `search_files(query, path?)` — буквальная подстрока, пути, строки,
  `scannedFiles`, `totalFiles`, `skipped` и `truncated`;
- `propose_file(path, baseHash, content? | edits?)` — сохранённое предложение
  с diff. Для нового файла нужны `baseHash: null` и `content`. Для обновления
  сначала требуется `read_file` в том же запросе. `edits` — массив
  `{ oldText, newText }`; каждый `oldText` должен встречаться ровно один раз.

Чтение и поиск охватывают tracked и новые неигнорируемые текстовые файлы
в `src/`, `scripts/`, `tests/`, Markdown в `docs/`, `README.md`, `AGENTS.md`
и выбранные корневые конфигурации. Это разрешённый список, не произвольный
доступ к диску. `list_files` показывает только tracked-пути; новые файлы
доступны через поиск и чтение.

Запись разрешена только в `README.md` и `docs/**/*.md`. Файлы инструкций
`AGENTS.md`, `CLAUDE.md`, `SKILL.md`, скрытые компоненты пути, символические
и дополнительные жёсткие ссылки защищены. `.env`, `.git`, `.harness`, базы,
ключи и файлы вне разрешённого списка не читаются и не изменяются.
`git_diff` и `search_docs` в файловом режиме исключены, чтобы необработанный
diff или старый RAG-снимок не обходили правила чтения.

Здесь действует существующая модель доверия локального учебного приложения:
отдельного входа оператора нет. Проверка `Origin` защищает от запросов
другого сайта, но не заменяет авторизацию. Пользователь с сетевым доступом
к приложению может подготовить и применить изменения документации.
Прочитанные фрагменты передаются настроенному провайдеру LLM.

## Данные, лимиты и запуск

Предложения хранятся в `data/file-assistant.sqlite`, таблица
`file_proposals(id, payload)`. Payload содержит содержимое, diff, целевой
хеш, корень, ветку, HEAD, даты и статус. SQLite/WAL/SHM игнорируются Git.
Срок ограничивает применение; автоматического удаления истёкших записей нет.
Обмены чата в эту базу не сохраняются.

Все настройки — `src/lib/file-assistant-config.ts`: до 192 КиБ на файл,
250 строк / 20 000 символов за чтение, 1 000 файлов / 100 совпадений за поиск,
64 000 символов полного нового содержимого и 80 000 символов diff.
Точечные замены сохраняют остальной текст большого README.
Пропуски и усечение обозначаются явно. До 12 раундов, 24 вызовов инструментов,
4 вызовов за раунд; общий таймаут — 240 с.

Последние три рабочих раунда или восемь оставшихся вызовов отведены
на подготовку результата: доступны чтение целевого файла и `propose_file`,
а в последнем рабочем раунде — только предложение. Запрос только на чтение
может завершиться обычным ответом без создания документа. В финальном раунде
каталог сохраняется, а вызовы явно отключаются через `tool_choice: none`.
Если провайдер возвращает нецитируемые служебные вызовы DSML внутри текста,
запрос завершается ошибкой: такой текст не исполняется и не считается готовым
ADR. Примеры внутри Markdown-кода и цитат разрешены для объяснения формата.

Нужны существующие настройки `OPENAI_*` и модель с профилем DeepSeek Flash.
Новые зависимости, секреты и RAG-индекс для Day 34 не требуются.

```bash
git switch day-34
npm ci
npm run dev
# http://localhost:3000/day-34
npm run test:files
```
