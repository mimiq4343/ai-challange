# Автоматическое ревью PR — Day 32

GitHub Action [`ai-code-review.yml`](../.github/workflows/ai-code-review.yml)
анализирует новый PR и обновляет один комментарий при новых коммитах.
Результат содержит потенциальные баги, архитектурные проблемы и рекомендации
с важностью, ссылкой на изменённую строку и предложением исправления.

## Проверка в приложении

Откройте `/day-32` из меню дней. Выберите базовую и проверяемую ветки,
нажмите «Запустить ревью». По умолчанию сравниваются `main` и текущий `HEAD`.
Ветки берутся из Git-репозитория сервера; кнопка обновления перечитывает
локальные и уже известные remote refs, без `git fetch` и переключения веток.
Ревью учитывает только коммиты, а не несохранённые или незакоммиченные правки.

Во вкладке «Diff и файлы» видны patch и полный файл. Во вкладке «Результат
ревью» появляются потенциальные баги, архитектурные проблемы и рекомендации,
важность, исправления и исходные RAG-фрагменты. Журнал показывает индексацию
и анализ каждого файла. «Остановить ревью» отменяет запрос и дальнейший анализ.
Текущий пакет локальных эмбеддингов может закончить вычисление перед остановкой.
Обрыв потока не считается успешным завершением. Если отдельный файл не проверен,
отчёт помечается как частичный и перечисляет причины пропусков.

Этот запуск использует серверные `OPENAI_API_KEY` и `OPENAI_BASE_URL`, работает
до слияния workflow в `main` и не пишет комментарии в GitHub. Результат хранится
в состоянии открытой страницы; обновление страницы его очищает. Каждый запуск
строит отдельный временный RAG-индекс точного base SHA и удаляет его после работы.
Локальная модель эмбеддингов переиспользуется сервером.

API страницы:

- `GET /api/code-review/branches` — репозиторий GitHub, refs и их SHA;
- `POST /api/code-review` — JSON `{ "baseRef": "refs/heads/main", "headRef": "HEAD" }`.
  Допускаются только refs из серверного списка. Поток NDJSON содержит `progress`,
  `snapshot`, затем `result` либо `error`. `result` включает полный отчёт;
  наличие пропусков нужно проверять отдельно. POST ограничен тем же origin,
  размером 4096 байт и временем 45 минут. Ключи и URL провайдера в браузер не передаются.

## Запуск в GitHub

Workflow реагирует на `pull_request_target`: `opened`, `synchronize`,
`reopened`, `ready_for_review`. Черновики пропускаются. Новый запуск отменяет
предыдущий запуск того же PR.

Для включения workflow должен попасть в базовую ветку PR. Разработка дня
ведётся в `day-32`; слияние в `main` согласуется отдельно. Поэтому PR,
добавляющий сам workflow, ещё не получает ревью этим workflow.

В репозитории задаются:

- Actions Secret `OPENAI_API_KEY` — ключ существующего провайдера;
- Actions Variable `OPENAI_BASE_URL` — его OpenAI-совместимый URL;
- `GITHUB_TOKEN` выдаётся GitHub автоматически, отдельный PAT не нужен.

Модель закреплена в `CODE_REVIEW_CONFIG.model`: `deepseek-v4-flash`.
Лимиты, промпт и версия GitHub REST API находятся в
[`code-review-config.ts`](../src/lib/code-review-config.ts).
`OPENAI_MODEL` не меняет модель ревью.

Workflow явно запрашивает `contents: read` и `pull-requests: write`.
Он публикует обычный комментарий PR, а не решение `APPROVE` или `REQUEST_CHANGES`.
Настройка GitHub, разрешающая Actions утверждать PR, для этого не требуется.

## Сбор контекста

1. `actions/checkout` получает точный `base.sha` с полной историей и без
   сохранения токена в Git-конфигурации.
2. `fetchReviewHead` скачивает `refs/pull/<number>/head` и проверяет SHA из
   события. Рабочая копия остаётся на base. Токен передаётся Git через
   окружение, без аргументов командной строки.
3. `collectReviewSnapshot` вычисляет merge base и сравнивает его с head.
   Список файлов включает добавления, удаления и переименования. Файлы
   читаются непосредственно из Git-объектов, без checkout PR.
4. Для каждого выбранного файла модель получает полный текст, его diff,
   номера изменённых строк, diff остальных выбранных файлов PR и список
   пропусков. Удалённый или полностью опустошённый файл читается из merge
   base, остальные — из head. Если hunk только удаляет строки, замечание
   может указывать на ближайшую сохранившуюся строку head. В конце файла
   якорем служит его последняя строка. Для чистого переименования или
   изменения метаданных без строк используется `line: null`: ссылка на файл
   целиком, без выдуманного номера строки.

Из отправки исключены `.env*`, `data/`, `node_modules/`, символьные ссылки,
submodule, бинарные файлы и неподдерживаемые форматы. Поддерживаются
TypeScript/TSX, JavaScript/JSX, Markdown, JSON, YAML, CSS и `.gitignore`.
Неотслеживаемые файлы рабочего дерева не участвуют.

Внешние diff/textconv отключены. PR не запускает свои install-скрипты,
сборку, тесты или импорт модулей в процессе с секретами. Все исполняемые
скрипты и зависимости берутся из доверенного base SHA.
Это сохраняет доступ к LLM и возможность комментария для PR из форков.
Основание: [GitHub о `pull_request_target`](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target).

## RAG по документации и коду

Корпус читается из точного `base.sha`:

- `README.md` и `AGENTS.md`;
- `docs/**/*.md`;
- `src/**/*.ts` и `src/**/*.tsx`.

Каждый запуск строит свежий структурный индекс во временной SQLite.
Используются существующие `chunkDocuments`, локальная E5, проверка векторов
и косинусное ранжирование. Модель эмбеддингов и её контрольные суммы
закреплены в конфигурации Недели 6. Индексы Day 21–31 не меняются.
Параметры: чанки до 384 токенов, перекрытие 64, векторы Float32 размерности 384.

Запрос поиска составляется из пути файла, прежнего пути при переименовании
и изменённых строк. Для каждого
файла выбираются до трёх фрагментов документации и до пяти фрагментов кода.
Раздельные квоты сохраняют оба вида контекста. Поиск не гарантирует, что
найдены все зависимости; модель должна указывать нехватку сведений.
Для обычных правок чанки AST, содержащие только imports, исключены из выдачи
кода, чтобы лексическое сходство путей не занимало всю квоту вместо
реализаций. При переименовании imports допускаются: в них видны зависимости
от старого пути.

Фрагменты имеют `S1…`, путь, раздел, строки и текст. Индекс привязан к
base SHA, а все ссылки в комментарии ведут на неизменяемые SHA. Промпт
объясняет, что RAG описывает base до PR, и требует учитывать согласованные
изменения остальных файлов PR.

Индекс удаляется после запуска. Веса E5 хранятся в игнорируемом
`data/models/`; в GitHub runner они скачиваются с проверкой SHA-256.

## Проверка и публикация ответа

LLM возвращает JSON с `findings` и `limitations`. Перед публикацией
проверяются схема, категория и важность, непустые пояснения, допустимый
якорь изменения и существование указанных `sourceIds`. `line: null`
принимается только при отсутствии строковых якорей. Незавершённый stream,
таймаут, неизвестная ссылка и некорректный JSON не считаются успешным ревью.
Семантическая верность замечаний остаётся ограничением LLM.

Markdown собирает приложение. Текст модели экранируется, упоминания
пользователей обезвреживаются. В комментарии есть счётчик проверенных файлов,
список пропусков и ограничения. Ошибка одного файла не мешает остальным,
но оставляет этот файл непроверенным и завершает CLI с кодом 1.
Сырые ответы API и ключи в диагностику не выводятся.

Публикация находит только комментарий `github-actions[bot]` с маркером
`<!-- flash-ai-code-review:day-32 -->`. Остальные комментарии не меняются.
До публикации повторно проверяются head SHA, base SHA и открытое состояние
PR. При несовпадении SHA или закрытом PR комментарий не обновляется.
Автоматических повторов запросов нет.

Результаты:

- `data/code-review/review.md` — комментарий и Actions Summary;
- `data/code-review/review.json` — полный контекст и структурированное ревью,
  либо `status: failed` с SHA и причиной общей ошибки. Новый запуск заменяет
  результат предыдущего.

Workflow сохраняет каталог как артефакт на семь дней, в том числе после
ошибки. Комментарий ограничен 60 000 символами; при сокращении перечисляет
число неуместившихся замечаний, непроверенных файлов и ограничений,
сохранённых в полном JSON. Общая ошибка заменяет прежний комментарий сообщением о
неудаче для текущего SHA.

## Лимиты

За запуск выбираются до 30 файлов: не более 100 000 байт текста и 30 000
символов diff на файл, суммарно до 180 000 символов текста и diff.
Файлы сверх лимитов перечисляются как непроверенные, без обрезания патча.
RAG-корпус ограничен 4 000 000 символов, отдельный файл — 2 000 000 байт;
превышение прерывает запуск с явной ошибкой.

Таймаут одного файла — 240 с, Git и GitHub API — 30 с. Лимит ответа LLM —
16 384 токена, до восьми замечаний на файл. Таймаут всего job — 45 минут.
Исчерпание времени job может остановить публикацию; состояние видно в Actions.

## Локальная проверка

```bash
npm ci
# OPENAI_BASE_URL и OPENAI_API_KEY читаются из .env.local.
# Укажите полные SHA двух коммитов, имеющихся в локальном Git.
npm run review:pr -- --base <BASE_SHA> --head <HEAD_SHA> --repository owner/repo
npm run test:code-review
```

Локальный режим не обращается к GitHub и не публикует комментарий. RAG
работает локально; выбранные diff, тексты файлов и RAG-фрагменты отправляются
провайдеру LLM. Режим `--event "$GITHUB_EVENT_PATH"` предназначен для Actions:
он дополнительно получает head и публикует комментарий через `GITHUB_TOKEN`.
