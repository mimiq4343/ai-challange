# Day 7: сохранение контекста в SQLite

## Цель

Добавить агенту постоянную историю нескольких диалогов. Пользователь создаёт,
выбирает и удаляет диалоги в боковой панели. Сообщения сохраняются в SQLite и
восстанавливаются после полного перезапуска Next.js, поэтому агент продолжает
разговор с прежним контекстом.

## Объём

В задачу входят:

- несколько независимых диалогов;
- хранение пользовательских и агентских сообщений в SQLite;
- восстановление списка диалогов и сообщений после перезапуска процесса;
- создание, выбор и удаление диалогов;
- автоматическое название по первому сообщению;
- потоковый ответ LLM;
- отдельная страница `/day-7`;
- практическая проверка памяти через полный рестарт приложения.

Не входят авторизация, разделение истории между пользователями, синхронизация
между устройствами, переименование, поиск, экспорт, пагинация и облачная база.
Приложение остаётся локальным однопользовательским стендом.

## Технические ограничения

- Runtime: Node.js 24.19.0.
- Framework: Next.js 16 App Router.
- Хранилище: встроенный `node:sqlite`; внешняя ORM и runtime-зависимость не
  нужны.
- `node:sqlite` требует Node.js не ниже 22.13. Проект фиксирует это требование в
  README.
- Типы Node.js обновляются до совместимой 24-й основной версии.
- Файл БД: `<project>/data/chat.sqlite`.
- `data/*.sqlite`, `data/*.sqlite-shm` и `data/*.sqlite-wal` исключаются из git.

## Модель данных

```sql
CREATE TABLE IF NOT EXISTS conversations (
  id TEXT PRIMARY KEY,
  title TEXT NOT NULL,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
) STRICT;

CREATE TABLE IF NOT EXISTS messages (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  conversation_id TEXT NOT NULL
    REFERENCES conversations(id) ON DELETE CASCADE,
  role TEXT NOT NULL CHECK (role IN ('user', 'assistant')),
  content TEXT NOT NULL,
  created_at TEXT NOT NULL
) STRICT;

CREATE INDEX IF NOT EXISTS messages_conversation_id_id
  ON messages(conversation_id, id);
```

Идентификатор диалога создаётся через `crypto.randomUUID()`. Время хранится как
UTC ISO 8601. Порядок сообщений определяется возрастающим `messages.id`, список
диалогов — убывающим `updated_at`.

Новый диалог получает название «Новый диалог». При первом успешном обмене
название заменяется нормализованным первым пользовательским сообщением,
обрезанным до 60 символов. Последующие сообщения название не меняют.

## SQLite и жизненный цикл

`SqliteConversationStore` владеет одним `DatabaseSync` и предоставляет операции:

- `listConversations()`;
- `createConversation()`;
- `getConversation(id)`;
- `getMessages(conversationId)`;
- `saveExchange(conversationId, userContent, assistantContent)`;
- `deleteConversation(id)`;
- `close()` для тестов и корректной смены экземпляра.

При открытии соединения хранилище:

1. создаёт каталог `data`, если его нет;
2. открывает БД с ненулевым busy timeout;
3. включает foreign keys;
4. переводит журнал в WAL;
5. создаёт таблицы и индекс через идемпотентную схему.

Все значения передаются prepared statements. `saveExchange` выполняет вставку
обоих сообщений, обновление `updated_at` и возможную смену заголовка одной
транзакцией. Удаление диалога каскадно удаляет сообщения.

Production-код получает хранилище через модульный `getConversationStore()`.
Экземпляр кэшируется в `globalThis`, чтобы Next.js hot reload не открывал новые
соединения. Тесты создают независимые экземпляры с явным путём к временной БД.

## Агент и сохранение контекста

Существующий `ChatAgent` остаётся низкоуровневой сущностью Day 6: добавляет
system prompt, вызывает OpenAI-совместимый API, проверяет ответ и превращает SSE
в поток текста.

Новый `PersistentChatAgent` композиционно использует `ChatAgent` и
`SqliteConversationStore`. Он не дублирует HTTP-клиент.

Алгоритм `respond(conversationId, content, signal)`:

1. убедиться, что диалог существует;
2. загрузить сохранённые сообщения;
3. добавить новый пользовательский запрос только в контекст текущего вызова;
4. вызвать `ChatAgent.respond()`;
5. передавать дельты ответа клиенту и одновременно собирать полный текст;
6. после штатного завершения потока вызвать `saveExchange`;
7. при отказе API или обрыве потока не сохранять незавершённый обмен.

Так пользователь и ответ появляются в БД вместе. После успешного завершения
потока перезапуск не может восстановить половину обмена. Если процесс завершён
во время генерации, последняя незавершённая пара исчезает, а ранее сохранённая
история остаётся целой.

Day 6 продолжает работать через `/api/chat`. Day 7 использует отдельные маршруты
и persistent-agent, поэтому учебные реализации обоих дней остаются доступными.

## HTTP API

### `GET /api/conversations`

Возвращает диалоги по `updated_at DESC`:

```json
{
  "conversations": [
    {
      "id": "uuid",
      "title": "Название",
      "createdAt": "2026-09-13T12:00:00.000Z",
      "updatedAt": "2026-09-13T12:01:00.000Z"
    }
  ]
}
```

### `POST /api/conversations`

Создаёт пустой диалог и возвращает его с HTTP 201.

### `GET /api/conversations/:id`

Возвращает диалог и его сообщения. Несуществующий ID получает HTTP 404.

### `DELETE /api/conversations/:id`

Удаляет диалог и сообщения. Успех — HTTP 204, неизвестный ID — HTTP 404.

### `POST /api/conversations/:id/messages`

Принимает:

```json
{ "content": "Сообщение пользователя" }
```

Пустая или нестроковая строка получает HTTP 400. Неизвестный диалог получает
HTTP 404. Успешный ответ — `text/plain` поток LLM. Ошибки конфигурации агента
возвращаются как HTTP 500, ошибки провайдера — HTTP 502.

После завершения потока клиент повторно получает список диалогов, чтобы увидеть
серверное название и новый порядок.

## Серверный рендер и клиентское состояние

`/day-7` — серверный компонент. Он загружает список диалогов и сообщения самого
свежего диалога напрямую из SQLite и передаёт их клиентскому
`ConversationWorkspace`. Начальная загрузка не делает дополнительный запрос из
`useEffect`.

Клиент хранит только состояние текущего экрана:

- список и активный ID;
- показанные сообщения;
- текст ввода;
- состояние генерации;
- состояние мобильной панели и подтверждения удаления;
- локальную ошибку действия.

SQLite остаётся источником истины. При ошибке потокового ответа клиент повторно
загружает активный диалог и удаляет несохранённую оптимистическую пару.

Если диалогов нет, показывается пустой чат. Отправка первого сообщения сначала
создаёт диалог через API, затем отправляет сообщение. Кнопка «Новый диалог» явно
создаёт и выбирает пустой диалог.

## Интерфейс

На desktop рабочая область делится на sidebar около 280 px и чат. Sidebar
содержит:

- кнопку «Новый диалог»;
- список по времени последнего сообщения;
- активное состояние выбранной строки;
- кнопку удаления с доступным именем;
- подпись «SQLite · автосохранение».

Каждая строка целиком выбирает диалог. Кнопка удаления является отдельным
элементом и не запускает выбор строки. Удаление требует подтверждения с явными
действиями «Отмена» и «Удалить». После удаления активного диалога выбирается
самый свежий из оставшихся; при пустом списке показывается пустое состояние.

На ширине меньше desktop sidebar становится выезжающей панелью поверх контента.
Её открывает кнопка меню в заголовке чата; выбор диалога закрывает панель. Escape
закрывает панель или подтверждение. Backdrop закрывает только панель, но не
подтверждение удаления.

Интерактивные области имеют размер не меньше 44×44 px, видимый keyboard focus и
не зависят только от hover. Во время генерации переключение, создание и удаление
диалогов блокируются с визуальным disabled-состоянием. Кнопка остановки
генерации остаётся доступной.

Существующие цветовые токены, Geist, Markdown-рендер и стиль Flash Chat
сохраняются. Новая палитра и второй набор компонентов не вводятся.

## Ошибки

- Ошибка начального чтения SQLite прерывает рендер `/day-7` с явной серверной
  ошибкой; пустая выдуманная история не показывается.
- Ошибки создания, загрузки и удаления показываются рядом с рабочей областью.
- Диалог удаляется из UI только после HTTP 204.
- Ошибка LLM не сохраняет текущий обмен и не уничтожает предыдущие сообщения.
- Неизвестный выбранный диалог приводит к обновлению списка, а не к созданию
  фиктивного объекта.
- Ошибки не проглатываются; boundary добавляет контекст и сохраняет исходную
  причину там, где она доступна.

## Проверка

### Постоянный тест хранилища

Тест на `node:test` использует временную директорию:

1. создать хранилище и диалог;
2. сохранить обмен;
3. закрыть соединение;
4. открыть новый экземпляр на том же файле;
5. проверить диалог, название, роли, тексты и порядок сообщений;
6. удалить диалог;
7. проверить каскадное удаление.

Тест защищает наблюдаемый контракт восстановления, а не внутренние SQL-вызовы.

### Практический тест приложения

1. запустить Next.js и открыть `/day-7`;
2. создать диалог;
3. отправить «Запомни кодовое слово: КЕДР»;
4. дождаться законченного ответа;
5. подтвердить наличие пары сообщений в SQLite;
6. полностью остановить процесс Next.js;
7. запустить приложение заново;
8. открыть `/day-7` и подтвердить восстановление списка и сообщений;
9. отправить «Какое кодовое слово я просил запомнить?»;
10. подтвердить ответ «КЕДР»;
11. удалить диалог;
12. перезапустить приложение и подтвердить, что диалог не восстановился.

Проверка интерфейса выполняется на desktop и mobile: отсутствие горизонтального
скролла, открытие и закрытие drawer, keyboard focus, выбор и удаление диалога.

## Совместимость и прежний код

`/api/chat`, `ChatAgent`, компонент `Chat` и страница `/day-6` остаются
используемыми и не являются legacy. Day 7 не меняет их контракт. Общую логику
вызова LLM повторно не реализуем; persistent-agent использует `ChatAgent`.
