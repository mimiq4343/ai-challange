# AI Advent Challenge #9

Автор: **Roman Sukhin** (@mimiq43).

Одно Next.js-приложение для заданий **AI Advent Challenge #9**. Каждый день
разрабатывается в отдельной ветке и вливается в `main` после проверки. Сейчас в
`main` собраны дни с 1 по 15: измерение токенов, сжатие истории, стратегии
управления контекстом, модель памяти, персонализация, формализованное состояние
задачи с предусловиями переходов и инварианты проекта, из-за которых запрос может
не дойти до модели.
Персонализация Day 12 выключена флагом `personalization`; код и данные профилей
сохранены.

Стек: Next.js 16 (App Router), React 19, TypeScript, Tailwind CSS v4 и встроенный
`node:sqlite`. Требуется Node.js **22.13 или новее**. LLM подключается через
любой OpenAI-совместимый API.

## Day 16 · Подключение MCP — ветка `day-16`

Страница `/day-16` переиспользует агента Day 15. В панели можно сохранить имя и
HTTPS URL MCP-сервера, проверить соединение, увидеть инструменты и удалить
подключение. Настройки хранятся в SQLite; правую панель можно скрыть и вернуть.
Поддерживается Streamable HTTP без авторизации. Инструменты моделью не вызываются.

После `npm ci` запустите приложение (`npm run dev`) и, в отдельном терминале,
`MCP_HOST=0.0.0.0 MCP_PORT=3001 npm run mcp:server`. Docker не нужен.
Конфигурация прокси: [`deploy/mcp.Caddyfile`](deploy/mcp.Caddyfile).
Проверка через HTTPS: `npm run mcp:list -- https://mcp.yees.ai/mcp`.
Сервер возвращает `add` и `get_current_time`; проверка SDK закрывает соединение
после чтения всех страниц `tools/list`. В UI показывается время проверки, не
постоянный статус соединения. Регрессионные проверки: `npm run test:mcp`.
Код клиента: [`src/lib/mcp-client.ts`](src/lib/mcp-client.ts); точка запуска
сервера: [`scripts/mcp-server.ts`](scripts/mcp-server.ts).

## Хронология

### Day 1 · Лендинг-чат — страница `/`

Flash Chat: лендинг с полноэкранным чатом для любой OpenAI-совместимой модели.
Стриминг ответов по SSE, Markdown-рендер, остановка генерации и новый диалог.
Ключ и конфиг провайдера остаются на сервере.

### Day 2 · Формат ответа — страница `/day-2`

Один запрос сравнивается бок о бок без ограничений и через тематического агента
«Кино-консьерж» с JSON-схемой, лимитом ответа, stop sequence и системной ролью.

### Day 3 · Способы рассуждения — страница `/day-3`

Одна задача решается четырьмя способами: прямой ответ, пошаговое решение,
мета-промпт и группа экспертов. Ответы автоматически сверяются с эталоном, а
сводная таблица сравнивает точность, время, длину и число запросов к API.

### Day 4 · Температура — страница `/day-4`

Один запрос выполняется по три раза при `temperature` 0, 0.7, 1.2 и 1.7.
Приложение измеряет точность и разнообразие, а отдельный запрос-судья оценивает
креативность и связность.

### Day 5 · Слабая, средняя и сильная модель — страница `/day-5`

Один запрос при одинаковых настройках уходит на три модели разных классов.
Поток NDJSON содержит ответы и метрики: время до первого токена, полное время,
скорость, число токенов и стоимость. Качество проверяется эталоном и слепым
LLM-судьёй.

### Day 6 · Первый агент — страница `/day-6`

`ChatAgent` инкапсулирует системную роль, конфигурацию провайдера, запрос к LLM,
обработку SSE и ошибки. `/api/chat` остаётся тонкой HTTP-границей, а интерфейс
потоково показывает Markdown-ответ.

### Day 7 · Сохранение контекста — страница `/day-7`

Пользователь создаёт несколько независимых диалогов, выбирает их в sidebar и
удаляет вместе с сообщениями. На мобильных sidebar работает как drawer.
Сохранённая история восстанавливается после полного рестарта Next.js и снова
передаётся LLM при продолжении разговора.

```text
Browser → conversation API → PersistentChatAgent → SQLite history
                                      │
                                      └→ ChatAgent → LLM
```

`PersistentChatAgent` перед каждым вызовом загружает сообщения выбранного
диалога из SQLite. Только после штатного завершения stream он одной транзакцией
сохраняет пару `user + assistant`; оборванный ответ не оставляет половину обмена.

### Day 8 · Токены и переполнение контекста — страница `/day-8`

Перед каждым запросом сервер считает системный промпт, историю, новое сообщение
и резерв ответа локальным официальным токенизатором DeepSeek. После завершения
stream фактические `prompt_tokens`, `completion_tokens`, cache split и стоимость
сохраняются в SQLite вместе с обменом. Локальная разбивка помечается как
`estimate`; итоговые значения провайдера остаются источником истины.

Интерфейс показывает рост текущего контекста, накопительные токены и стоимость,
а также сравнивает короткий и длинный сценарии. Отдельный подтверждаемый тест
делает ровно один запрос к OpenRouter Embeddings с input больше лимита 32 768
токенов модели `nvidia/nemotron-3-embed-1b:free`. Retry нет; большой input и
embedding vector не сохраняются и не логируются.

Фактический прогон: локальный токенизатор насчитал 33 288 токенов в input из
221 919 символов. OpenRouter вернул HTTP 400 по собственному ограничению 65 536
символов, то есть отклонил payload раньше проверки token context window.
Сохранённый outcome — `rejected`, provider token count отсутствует, длительность
849 ms, стоимость $0.

### Day 9 · Сжатие истории — страница `/day-9`

Полная история остаётся в SQLite. Старые сообщения сворачиваются immutable
checkpoint-ами по 10 сообщений, а модели передаются summary и несжатый buffer.
Provider usage измеряет экономию; отдельный benchmark делает ровно четыре
последовательных LLM-вызова и слепо сравнивает full/compressed ответы.

### Day 10 · Стратегии контекста — страница `/day-10`

Один агент переключается между Sliding Window, Sticky Facts и двумя
независимыми ветками от checkpoint. Общий benchmark сравнивает качество,
стабильность, provider tokens и удобство без summary.

### Day 11 · Модель памяти агента — страница `/day-11`

Память агента разделена на три слоя с раздельным хранением и явной
маршрутизацией записи:

| Слой | Что хранит | Область | Носитель |
| --- | --- | --- | --- |
| STM · краткосрочная | дословное окно последних 8 сообщений | диалог | `messages` |
| WM · рабочая | активная задача: цель и слоты `факт`, `ограничение`, `шаг`, `вопрос` | диалог | `memory_working_tasks`, `memory_working_slots` |
| LTM · долговременная | профиль, решения и знания | все диалоги | `memory_long_term` |

```text
system → [LTM-блок] → [WM-блок] → окно STM → запрос
                                     │
                                     └→ ответ → роутер памяти → LTM и WM
```

После каждого завершённого обмена отдельный запрос-роутер решает, что и в какой
слой записать, и возвращает строгий JSON с причиной каждой записи. Обмен
сохраняется раньше и не зависит от роутера: его сбой оставляет память без новых
записей, но не теряет диалог. LTM уникальна по паре «тип + ключ», поэтому
повторный факт обновляет запись, а не копит дубликаты.

Инспектор памяти показывает содержимое всех трёх слоёв, журнал записей с
причинами и позволяет добавлять и удалять записи вручную. Тумблеры отключают
любой слой: выключенный слой не попадает в промпт и стоит ноль токенов. Строка
телеметрии под полем ввода показывает вклад `sys`, `LTM`, `WM`, `STM` и запроса,
процент контекстного окна, накопленную стоимость и стоимость роутера.

### Day 12 · Персонализация ассистента — страница `/day-12`

Поверх трёх слоёв памяти появляется профиль пользователя. Он описывает, как
разговаривать, и владеет собственной долговременной памятью:

| Что настраивается | Значения |
| --- | --- |
| Роль | свободный текст, например «backend-инженер» |
| Тон | нейтральный, дружелюбный, официальный, прямой |
| Длина | кратко, сбалансированно, подробно |
| Формат | связный текст, списки, таблицы, сначала код |
| Язык | русский, английский, язык пользователя |
| Уровень | начальный, средний, экспертный |
| Ограничения | свободный список: «без эмодзи», «не извиняйся» |

```text
system → профиль → LTM профиля → WM → окно STM → запрос
```

Активен всегда ровно один профиль, и это серверное состояние. Переключение
профиля меняет и стиль ответа, и известные агенту факты: `memory_long_term`
привязана к `profile_id`, поэтому у «Инженера» и «Новичка» разные знания о
пользователе. Существующие записи Day 11 миграция переносит в профиль
«Основной», а `/day-11` работает с памятью активного профиля.

Роутер памяти получает третий слой: фраза «отвечай короче» меняет длину на
`brief`, «давай сразу код» — формат на `code_first`, «без эмодзи» добавляет
ограничение. Значения полей проверяются по перечислениям, каждая запись видна в
журнале с причиной и откатывается вручную. Тумблер `PROF` отключает слой
целиком: блок не уходит в промпт и стоит ноль токенов.

Проверено на одном вопросе «Как проверить, что SQLite-миграция прошла успешно?»:
профиль «Инженер» (прямой тон, кратко, сначала код, эксперт, без эмодзи) ответил
блоками SQL и Python без вступления, профиль «Новичок» (дружелюбный, подробно,
связный текст, начальный уровень) — развёрнутым объяснением с аналогией и
нумерованными шагами.

### Day 13 · Состояние задачи — страница `/day-13`

Задача агента описана конечным автоматом и принадлежит профилю, а не диалогу,
поэтому переживает смену разговора.

```text
planning ──► execution ──► validation ──► done
                │  ▲           │  │
                ▼  └───────────┘  ▼
             blocked          cancelled   (пауза — отдельный флаг на любом этапе)
```

В состоянии хранятся этап, список шагов со статусами, указатель текущего шага и
ожидаемое действие: кто ходит следующим и что именно делает. Переход предлагает
агент, сервер валидирует его по таблице переходов, человек может вмешаться
кнопками. Недопустимый переход не меняет состояние и попадает в журнал как
`rejected`; предложение перейти в текущий же этап считается no-op и журнал не
засоряет.

Задачу не нужно заводить руками: если в запросе видна многошаговая работа
(«составь план питания на неделю»), агент возвращает **предложение задачи**, и в
панели появляется карточка «Агент предлагает задачу» с кнопками «Завести» и
«Отклонить». Пока живая задача есть, новые предложения игнорируются — автомат
один. Одиночные вопросы задачей не становятся.

Пока слой задачи включён, к системному промпту добавляются правила автомата: на
этапе планирования агент выдаёт нумерованный список из 3–7 шагов и ждёт
подтверждения, на этапе выполнения работает ровно над текущим шагом и заканчивает
ответ тем, что сделано и что требуется дальше. Без этих правил состояние
оставалось справкой, и агент отвечал одним большим сообщением.

Ключевая инварианта паузы: пока задача приостановлена, любые переходы агента
отклоняются — двигать автомат снова может только человек. При этом агент
продолжает отвечать: состояние уходит в промпт отдельным блоком, поэтому после
паузы и даже в новом диалоге он продолжает с того же шага.

```text
Состояние задачи «Запустить рассылку»: этап выполнение, пауза снята.
Шаг 2 из 4: «Подготовить письмо».
Выполнено: 1) Собрать и выверить базу.
Осталось: 3) Настроить и протестировать отправку; 4) Отправить и зафиксировать.
Ожидается: агент — выполнить текущий шаг.
```

Проверено вживую: агент составил план из четырёх шагов и записал его в
`planning`, закрыл первый шаг и перешёл в `execution`, на паузе его попытка уйти
в `validation` дала запись `rejected`, а в новом диалоге на одно слово
«Продолжаем» он сразу выдал черновик письма для шага 2 без повторных вопросов.

Персонализация Day 12 выключена флагом `personalization` в
`src/lib/feature-flags.ts`: блок профиля не попадает в промпт, предпочтения не
обучаются, `/api/profiles/*` отвечают 404, а `/day-12` показывает плашку вместо
панели. Таблицы профилей и `profile_id` в долговременной памяти сохранены —
возврат стоит одной правки `false → true`.

### Day 14 · Инварианты и ограничения — страница `/day-14`

Инвариант — правило, которое ассистент не имеет права нарушать: выбранная
архитектура, принятое техническое решение, ограничение по стеку или
бизнес-правило. Правила принадлежат профилю, живут в `memory_invariants` и
действуют во всех диалогах и задачах.

Отказ обеспечивают два контура:

```text
запрос → guard (проверка по своду правил) → conflict? → отказ сервера, модель не вызывается
                                          → allow    → промпт с блоком инвариантов → ответ
```

Guard — отдельный дешёвый вызов без рассуждений: он возвращает вердикт,
идентификаторы нарушенных правил, объяснение и альтернативу. При конфликте
чат-модель не вызывается вообще: сервер сам отдаёт отказ, поднимает счётчик
блокировок у правила и пишет событие `violation_blocked`. Нечитаемый ответ guard
трактуется как `allow` — сбой страховки не должен превращаться в отказ
обслуживания. При пустом своде правил guard не вызывается.

Второй контур — блок инвариантов первым в промпте, сразу после базовой роли:

```text
Инварианты проекта, нарушать запрещено:
- [стек] Только PostgreSQL, без ORM. Почему: команда держит SQL под контролем.
Решение, нарушающее инвариант, предлагать нельзя даже как вариант.
```

Отказ выглядит так: цитата правила с обоснованием, объяснение конфликта,
альтернатива в рамках и напоминание, что правило меняется только в панели, а не
уговорами в диалоге. Снятое правило уходит в «Снятые» и возвращается кнопкой —
обе операции попадают в журнал. Агент может предложить новый инвариант, когда в
разговоре прозвучало решение-ограничение; оно вступает в силу после
подтверждения.

Проверено вживую: правило «Только PostgreSQL, без ORM» → запрос «перепишем
хранилище на MongoDB и подключим Prisma» → отказ с цитатой, счётчик блокировок 1
и запись в журнале; нейтральный вопрос про ускорение выборки прошёл обычным
путём; после снятия правила тот же запрос перестал блокироваться.

### Day 15 · Контролируемые переходы — страница `/day-15`

Day 13 дал автомат с таблицей переходов; Day 15 добавляет предусловия, без
которых «нельзя перепрыгнуть этап» остаётся декларацией.

| Переход | Предусловие | Причина отказа |
| --- | --- | --- |
| `планирование → выполнение` | план непуст и утверждён человеком | «Плана нет» / «План не утверждён» |
| `выполнение → проверка` | все шаги закрыты | «Осталось незакрытых шагов: N» |
| `проверка → готово` | инициатор — человек | «Финал принимает человек» |

План утверждается кнопкой «Утвердить план» или явной фразой в диалоге, которую
распознаёт роутер. Правка плана после утверждения снимает отметку и пишет
событие: иначе «утверждён» перестаёт что-либо значить.

Отклонённая попытка больше не теряется. Она сохраняется в задаче, показывается
в панели плашкой и попадает в блок промпта следующего обмена, поэтому агент
объясняет отказ сам:

> Не могу начать реализацию: переход в этап выполнения отклонён, потому что план
> ещё не утверждён… Что требуется от вас: подтвердить план целиком.

Кнопки переходов с невыполненным предусловием становятся неактивными и несут
причину в подсказке. Успешный переход и утверждение плана очищают отказ.

Проверено вживую: переход в выполнение без утверждения → 409 и объяснение
ассистента; после кнопки «Утвердить план» тот же переход прошёл; `выполнение →
готово` отклонён таблицей, `выполнение → проверка` — предусловием «осталось
незакрытых шагов: 3»; после закрытия шагов проверка и финал прошли.

## SQLite и API Day 7–15

История создаётся автоматически в `data/chat.sqlite`. SQLite работает в
WAL-режиме, foreign keys включены. Таблицы `conversations` и `messages` связаны
