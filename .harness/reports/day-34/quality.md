# Проверка Day 34

Дата: 2026-10-18. Ветка: `day-34`. Модель реальных запросов:
`deepseek-v4-flash`. Интерфейс: `/day-34`, настоящий локальный stdio MCP.

## Реальные сценарии

- **Поиск:** запрос об использованиях `ConversationSidebar`. Модель вызвала
  `search_files`, `list_files`, два `read_file` и уточняющий `search_files`.
  Нашла определение компонента, импорт и JSX в `conversation-workspace.tsx`,
  отделила текстовые упоминания. Первый поиск просмотрел 444 доступных файла,
  `skipped=[]`, `truncated=false`. Это буквальный поиск; полнота по алиасам
  и динамическим обращениям не проверяется.
- **Создание:** чтение `file-assistant-files.ts` и конфигурации, предложение
  `docs/day-34-browser-probe.md`. Четыре вызова, 13,6 с по интерфейсу.
  До Apply файла на диске не было. После Apply он появился: 3 813 байт.
- **Обновление:** чтение созданного документа и конфигурации, `propose_file`
  с `edits` для заголовка. Три вызова, 6,6 с. Diff содержал одну замену,
  после Apply заголовок изменился, остальной документ сохранился; 3 819 байт.
  Проверочный файл удалён после проверки и не входит в продукт.

Модель подготовила 31 строку при просьбе «до 30 строк». Наличие вызовов и
валидность diff не гарантируют соблюдения всех смысловых требований.
Результаты требуют просмотра перед применением.

## Пределы проверки

Запись в исходники не предусмотрена согласованным объёмом. Нет общей
транзакции нескольких файлов. Проверяется актуальность целевого файла,
но не всех исходников, прочитанных для документа. Origin не заменяет
авторизацию: сетевой доступ к приложению позволяет менять документацию.
Против одновременной враждебной замены каталогов локальным процессом
изоляция на уровне ОС не вводилась. Истёкшие предложения остаются в базе,
хотя применить их нельзя.

Пользователь повторил сценарий ADR, применил предложение и 2026-10-18 явно
разрешил слияние `day-34` в `main`. Полная интеграция заменяет ранее
подготовленный отдельный patch README.

Перед интеграцией повторены `npm run build`, `npm run test:files`,
`npm run test:mcp`, `npm run test:orchestration`, `npm run test:dev-assistant`
и `git diff --check`. Сборка и все 131 тест прошли. Браузерные проверки
выше относятся к реализации и исправлению ADR; при интеграции код не менялся.
Применённый пользователем `docs/adr/file-assistant.md` уже был untracked:
он сохранён локально и не включён в коммиты интеграции.

## Исправление ADR после сообщения пользователя

Пользователь показал DSML-разметку вызовов вместо ADR после 23 инструментов.
Детерминированный SSE-тест воспроизвёл принятие такой разметки как ответа
с `finish_reason: stop`. Отдельные тесты показали, что при одном или четырёх
вызовах за раунд весь бюджет мог уйти на чтение без подготовки файла.

Исправлены три участка: разметка отвергается на границе провайдера;
финальный запрос сохраняет каталог и использует явный `tool_choice: none`;
файловый режим резервирует три рабочих раунда / восемь вызовов на целевой
документ и предложение. Вне каталога текущего раунда вызовы не исполняются.
Запрос только на чтение по-прежнему завершается без создания файла.
Нативное значение `none` сверено с
[документацией DeepSeek](https://api-docs.deepseek.com/api/create-chat-completion).
Отдельный реальный запрос к `deepseek-v4-flash` с каталогом и
`tool_choice: none` вернул HTTP 200, текст «Готово» и ноль вызовов.

Ошибка провайдера непостоянна: первый повтор точного UI-примера до изменений
подготовил ADR за 8 вызовов и 39,8 с. После исправления тот же пример подготовил
106-строчный ADR за 5 вызовов и 42,9 с: `read_file`, `list_files`, ещё два
`read_file`, успешный `propose_file`. В карточке есть все четыре раздела,
diff и доступная кнопка «Применить»; служебной разметки в ответе нет.
На 390 px проверены отсутствие горизонтального переполнения и цели ≥44×44 px.
Из этого прогона нельзя сделать вывод об ускорении модели или гарантировать
успех каждого будущего ответа. Для разметки в тексте теперь есть явный отказ
вместо ложного успешного результата.

Независимое ревью выявило ложное срабатывание первого фильтра на примерах
DSML внутри Markdown-кода. Положительные тесты inline/fenced code сначала
упали. После применения существующего Markdown-парсера код и цитаты
пропускаются; необработанные вызовы, включая смесь цитаты и вызова,
по-прежнему отклоняются. Шесть положительных/отрицательных случаев прошли.
