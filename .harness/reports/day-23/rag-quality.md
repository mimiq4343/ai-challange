# Day 23: query rewrite, реранкинг и фильтрация

Дата измерений: 6 октября 2026 года. Первый прогон выполнен командой
`npm run rag:refinement-benchmark`, второй — кнопкой на `/day-23`.
Это измерение на небольшом корпусе проекта, а не общий рейтинг RAG-систем.

## Условия сравнения

Все режимы используют один снимок локального SQLite-индекса Day 22,
эмбеддинги `Xenova/multilingual-e5-small` размерности 384 и настроенную
модель `deepseek-v4-flash`. Индекс при сравнении не пересоздавался.
ID снимка: `704cbc82-6152-4baf-aea1-3e717e0de440`.

Параметры: `candidateK = 20`, `contextK = 5`, `minRelevance = 6`.
Порог включительный: оценка 6 проходит. Значения настраиваются в интерфейсе;
допустимы целые candidateK 1–40, contextK 1–10 и не больше candidateK,
minRelevance 0–10. Это оценка LLM по шкале 0–10, а не порог cosine similarity.
Порог 6 соответствует нижней границе частичного фактического ответа в рубрике:
оценки 4–5 означают общую тему без нужного факта. Это выбранная исходная
настройка; оптимальность порога и других top-K отдельным перебором не проверялась.

Сравниваются три режима:

- `baseline`: поиск исходного вопроса, первые пять фрагментов, один вызов LLM.
- `rewrite`: одна новая поисковая формулировка, первые пять фрагментов,
  два вызова LLM с учётом генерации ответа.
- `refined`: та же формулировка и те же двадцать кандидатов, дополнительная
  оценка каждого фрагмента, отсечение оценок ниже 6, сортировка и максимум
  пять фрагментов в ответе. Три вызова LLM с учётом генерации.

Генерация во всех режимах получает исходный вопрос. Исходники и эталонные факты
для контрольного ответа доступны только судье, а не rewrite, reranker или
генератору ответа. Метки a/b/c перед оценкой случайно переставляются.
Промпты, настройки, запросы, оценки кандидатов, ответы и статистика сохраняются
в `data/rag-refinement-comparison.json`; этот локальный файл исключён из git.

В наборе десять прежних вопросов по корпусу и два отрицательных вопроса:
о доставке DHL и о прогнозе урожая. Проверка попадания требует наличия
контрольного источника и конкретной строки evidence в окончательном контексте.
Это попадание контрольного фрагмента, а не ручная оценка каждого кандидата.

### Что изменилось на конкретном вопросе

Вопрос: «Как Flash Chat проверяет Bearer-токен MCP-запроса и идентификатор
профиля?» Обычный поиск вернул README и `token-counter.ts`; реализации
проверки в пяти фрагментах не оказалось. Ответ получил 2/10.

Rewrite дал запрос:

```text
Flash Chat проверка Bearer-токена MCP-запроса и идентификатора профиля; MCP request Bearer token verification, profile ID validation
```

`src/lib/mcp-auth.ts` появился третьим с cosine similarity 0.880747716784159.
Ответ с rewrite получил 10/10. Reranker оценил этот кандидат в 10/10,
оставил только его и убрал остальные девятнадцать фрагментов. Ответ после
фильтра получил 9/10: число источников сократилось с пяти до одного без
потери контрольного фрагмента. Улучшение попадания здесь даёт rewrite;
фильтр очищает контекст и не гарантирует повышение оценки каждого ответа.

На обоих отрицательных вопросах baseline и rewrite передали по пять
нерелевантных фрагментов. `refined` передал ноль и явно сообщил об отсутствии
подходящих сведений. Отброшенный контекст не используется как запасной вариант.

## Ограничения измерения

Судья использует ту же LLM, которая переписывает запрос, оценивает релевантность
и отвечает. Оценки ориентировочные и могут меняться между запусками.
Слепые метки убирают названия режимов, но стиль ответа и количество источников
остаются видны. Двенадцать вопросов недостаточны для статистического вывода.

На отрицательных вопросах судья поставил пустому контексту по 8, хотя ответы
честно признали отсутствие сведений. В обосновании он предпочёл перечисление
источников и более категоричное утверждение об отсутствии реализации.
Пустой найденный контекст позволяет утверждать отсутствие найденных сведений,
но не отсутствие функции во всём проекте. Поэтому оценки судьи следует читать
вместе с независимой метрикой пустого контекста и самими ответами.

Вопросы `chat-history` и `chat-completion` остаются промахами поиска нужной
реализации. После отбора фильтр не может вернуть источник, которого нет среди
кандидатов. Более точный поиск или другой размер кандидатов требует отдельного
измерения; результаты этого отчёта не подтверждают их эффект.

Повышение качества сопровождается дополнительными вызовами LLM: полный поток
в первом прогоне расходовал в среднем примерно в 4.74 раза больше токенов,
чем baseline, и занимал примерно в 4.64 раза больше времени. Уменьшение
финального контекста само по себе не означает уменьшение общих затрат.
