# Day 14: инварианты и ограничения состояния

## Цель

Дать ассистенту свод правил, которые он не имеет права нарушать: выбранная
архитектура, принятые технические решения, ограничения по стеку и бизнес-правила.
Правила хранятся отдельно от диалога, явно участвуют в рассуждении и приводят к
отказу, если запрос требует их нарушить.

Ветка `day-14` создана от `main`, где собраны дни 1–13.

## Утверждённые решения

- Отказ обеспечивают два контура: предварительная проверка запроса (guard) и
  жёсткий блок инвариантов в промпте.
- Инварианты принадлежат профилю и действуют во всех диалогах и задачах.
- При конфликте агент отказывает с дословной цитатой правила и альтернативой;
  изменить правило можно только явно, через панель.
- Инварианты вводятся вручную, а также предлагаются агентом с подтверждением.

## Данные

- `memory_invariants` — `profile_id` (FK, CASCADE), `category`
  (`architecture` | `tech_decision` | `stack` | `business_rule`), `statement`,
  `rationale`, `status` (`active` | `retired`), `blocked_count`, временные метки,
  `UNIQUE (profile_id, statement)`. Снятое правило уходит в `retired`, а не
  удаляется: иначе журнал отказов теряет опору.
- `memory_invariant_proposals` — кандидаты от агента: `category`, `statement`,
  `rationale`, `conversation_id`, `UNIQUE (profile_id, statement)`.
- `memory_invariant_events` — журнал: `created`, `updated`, `retired`,
  `restored`, `proposal_accepted`, `proposal_rejected`, `violation_blocked`;
  хранит `invariant_id`, `conversation_id`, текст запроса и объяснение.

Схему создаёт и мигрирует `memory-schema.ts`.

## Проверка запроса

`invariant-guard.ts` перед генерацией делает один не-стримовый вызов с
`reasoning_effort: "none"` и строгим JSON:

```json
{ "verdict": "allow" | "conflict", "invariantIds": [3],
  "explanation": "почему нарушает", "alternative": "что сделать вместо" }
```

- При пустом своде активных правил guard не вызывается вовсе.
- При `conflict` чат-модель не вызывается: сервер сам стримит отказ с цитатой
  правила, объяснением и альтернативой, увеличивает `blocked_count` и пишет
  событие `violation_blocked`.
- Невалидный ответ guard считается `allow`: страховка не должна превращаться в
  отказ обслуживания из-за сбоя разбора. Ошибка логируется один раз.
- Отказ сохраняется как обычный обмен `user + assistant`, чтобы история диалога
  оставалась честной.
- Ответ несёт заголовки `X-Invariant-Block` с идентификаторами правил.

## Промпт

Порядок: `system → инварианты → профиль → задача → LTM → WM → окно STM → запрос`.

```text
Инварианты проекта, нарушать запрещено:
- [стек] Только PostgreSQL, без ORM. Почему: команда держит SQL под контролем.
- [архитектура] Монолит без выделения микросервисов до 100k MAU.
Решение, нарушающее инвариант, предлагать нельзя даже как вариант.
```

`MemoryLayerTokens` получает `invariantTokens`, телеметрия — сегмент `INV`,
инспектор — отдельный тумблер. Выключенный слой отключает и блок, и guard:
это прямая демонстрация разницы в поведении.

## Предложения

Роутер памяти возвращает `invariantProposals: [{category, statement, rationale}]`,
когда в обмене прозвучало решение-ограничение. Правило вступает в силу только
после подтверждения в панели; отклонение тоже попадает в журнал.

## API

```text
GET    /api/invariants
POST   /api/invariants
PATCH  /api/invariants/:id
POST   /api/invariants/:id/retire
POST   /api/invariants/:id/restore
POST   /api/invariants/proposals/:id/accept
DELETE /api/invariants/proposals/:id
POST   /api/conversations/:id/invariant-messages
```

## Интерфейс `/day-14`

- Правый rail: `InvariantPanel` (правила по категориям со счётчиком блокировок,
  редактирование формулировки, снятие и восстановление, карточки предложений,
  журнал событий), ниже панель задачи Day 13 и инспектор памяти Day 11.
- Отказ приходит обычным сообщением ассистента: цитата правила, причина,
  альтернатива.
- Русский интерфейс, визуальная система Flash Chat, области минимум 44×44 px,
  bottom sheet на мобильных, без горизонтального overflow.

## Проверка

- `npm run test:invariants` — CRUD и уникальность правил, переход
  `active → retired → active` с журналом, каскад при удалении профиля, разбор
  вердикта guard (валидный, мусорный, неизвестные идентификаторы), блокировка без
  единого обращения к чат-модели, сохранение отказа как обмена, инкремент
  `blocked_count`, нулевой вклад выключенного слоя, разбор предложений роутера.
- Регресс: `test:tasks`, `test:memory`, `test:profiles`, `test:tokens`,
  `test:persistence`, `test:compression`, `test:context-strategies`.
- Живой сценарий: правило «Только PostgreSQL, без ORM» → запрос «возьмём MongoDB
  и Prisma» → отказ с цитатой и альтернативой → снятие правила → тот же запрос
  проходит.
