# Day 13: состояние задачи как конечный автомат

## Цель

Формализовать состояние задачи агента: этап, текущий шаг и ожидаемое действие.
Автомат должен переживать паузу на любом этапе и смену диалога: после
возобновления агент продолжает с того же шага и не переспрашивает уже
согласованное.

Ветка `day-13` создана от `main`, где собраны дни 1–12.

## Утверждённые решения

- Задача принадлежит профилю, а не диалогу, и доступна из любого разговора.
- Состояния: `planning`, `execution`, `validation`, `done`, `blocked`,
  `cancelled`. Пауза — ортогональный флаг, а не состояние.
- Переход предлагает агент, валидирует сервер, человек может вмешаться кнопками.
- Шаги — список с состояниями и указателем на текущий, а не одно текстовое поле.
- Персонализация Day 12 отключается флагом, но не удаляется.

## Отключение профилей

`src/lib/feature-flags.ts` содержит versioned-конфиг:

```ts
export const FEATURES = { personalization: false } as const;
```

При выключенном флаге:

- блок профиля не попадает в промпт, `profileTokens` всегда 0;
- роутер памяти не получает правил слоя `profile` и не пишет предпочтения;
- `/api/profiles/*` отвечают 404 с явным сообщением;
- `/day-12` показывает плашку вместо панели профиля, чат и память страницы
  продолжают работать;
- rail `/day-13` состоит из состояния задачи и инспектора памяти.

Таблицы `memory_profiles`, `memory_profile_constraints` и `profile_id` в
`memory_long_term` сохраняются: долговременная память Day 11 живёт внутри
профиля, и откат схемы означал бы потерю записей. При выключенном флаге всё
работает на профиле «Основной», а возврат персонализации стоит одну правку
`false → true`.

## Автомат

Разрешённые переходы (`task-machine.ts`, без БД и сети):

| Из | В |
| --- | --- |
| `planning` | `execution`, `cancelled` |
| `execution` | `validation`, `blocked`, `cancelled` |
| `validation` | `done`, `execution`, `blocked`, `cancelled` |
| `blocked` | `execution`, `validation`, `cancelled` |
| `done` | — |
| `cancelled` | — |

- `blocked` запоминает `blocked_from`, поэтому разблокировка возвращает ровно
  туда, откуда ушли; переход в другой этап из `blocked` отклоняется.
- Пауза возможна на любом нетерминальном этапе и не меняет ни этап, ни шаг.
- **Инварианта паузы:** пока `paused = 1`, сервер отклоняет любые переходы,
  предложенные агентом. Двигать автомат снова может только человек через
  `resume`. Каждый отклонённый переход пишется в журнал как `rejected`.
- `done` и `cancelled` терминальны.

## Данные

- `task_runs` — `profile_id` (FK, CASCADE), `title`, `goal`, `stage`, `paused`,
  `expected_actor` (`agent` | `user`), `expected_action`, `blocked_from`,
  `blocked_reason`, `current_step_id`, временные метки. Частичный уникальный
  индекс `ON task_runs(profile_id) WHERE stage IN ('planning', 'execution',
  'validation', 'blocked')` — не больше одной живой задачи на профиль.
- `task_steps` — `run_id` (CASCADE), `position`, `title`, `status`
  (`pending` | `active` | `done` | `skipped`), `result`, `UNIQUE (run_id, position)`.
- `task_events` — журнал: `kind` (`transition` | `step` | `pause` | `resume` |
  `rejected`), `origin` (`agent` | `user`), `from_stage`, `to_stage`, `reason`,
  `conversation_id`, `assistant_message_id`.

Схему создаёт и мигрирует тот же `memory-schema.ts`.

## Промпт

Порядок: `system → профиль → состояние задачи → LTM → WM → окно STM → запрос`.

```text
Состояние задачи «Перенос памяти под профили»: этап execution, пауза снята.
Шаг 3 из 6: «Перенести записи LTM».
Выполнено: 1) Собрать требования; 2) Спроектировать схему.
Осталось: 4) Обновить API; 5) Проверить миграцию; 6) Обновить документацию.
Ожидается: агент выполняет текущий шаг.
План и решения уже согласованы — не переспрашивай их заново.
```

`MemoryLayerTokens` получает `taskTokens`, телеметрия — сегмент `TASK`,
инспектор — отдельный тумблер слоя.

## Переходы от агента

Роутер памяти возвращает дополнительный объект:

```json
{ "taskState": { "transition": "execution", "completedSteps": [3],
                 "newSteps": ["…"], "expectedActor": "user",
                 "expectedAction": "…", "block": null } }
```

`newSteps` принимаются только на этапе `planning`. Всё применяется одной
транзакцией: переход, отметки шагов, указатель текущего шага и журнал.

## Агент

Отдельный третий агент не создаётся: `PersonalizedChatAgent` получает
опциональный слой задачи и опцию `personalization`, поэтому Day 12 и Day 13
используют один пайплайн `flush` вместо трёх копий.

## Интерфейс `/day-13`

- Правый rail: `TaskStatePanel` (цепочка этапов с текущим, пауза и
  возобновление, блокировка и отмена, список шагов со статусами, ожидаемое
  действие, журнал событий) и ниже инспектор памяти Day 11.
- Телеметрия под полем ввода дополняется сегментом `TASK`.
- Русский интерфейс, визуальная система Flash Chat, области минимум 44×44 px,
  bottom sheet на мобильных, без горизонтального overflow.

## Проверка

- `npm run test:tasks` — все разрешённые и запрещённые пары переходов, одна
  живая задача на профиль, возврат из `blocked` в `blocked_from`, отклонение
  агентских переходов на паузе с записью `rejected`, движение указателя шагов,
  терминальность `done` и `cancelled`, содержимое блока задачи в промпте,
  нулевой вклад выключенного слоя, отключённая персонализация не добавляет блок
  профиля.
- Регресс: `test:profiles`, `test:memory`, `test:persistence`, `test:tokens`,
  `test:compression`, `test:context-strategies`.
- Живой сценарий: план в `planning` → `execution` → выполненный шаг → пауза →
  новый диалог → «продолжаем» → агент называет текущий шаг и не переспрашивает
  согласованное → `validation` → `done`; отдельно проверяется запись `rejected`
  при попытке агента двинуть автомат на паузе.
